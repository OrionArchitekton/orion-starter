# Starter continuity profile

Status: private implementation authorized by Dan, 2026-10-17. Publication remains subject to full-package review and separate approval.

## Outcome and scope

Two cooperating local workers continue one selected task using independently acquired ownership. The producer observes a public synthetic page, releases its browser, records bounded context, and yields the unfinished PM task. The consumer reviews that exact context, acquires its own PM claim and native browser lease, independently observes the expected result, cleans up, and completes the task with current evidence.

Deliver one optional profile in the existing orion-starter distribution. Retain the PM/browser profile and its interfaces. Proposed distribution version: **0.2.0-rc.1**, explicitly a preview. Component releases remain independent: PM 0.1.1, browser 0.1.0 and Handoff 0.1.0. Exact artifacts and implementation units belong in the [release plan](../docs/plans/2026-10-17-starter-continuity-release-plan.md).

The profile demonstrates a cooperating local workflow. It does not add a daemon, shared SDK, approval broker, cross-host execution fencing, native harness hooks, vendor session readers, account access, phone or Remote Hands integration. It does not migrate an estate installation. The task has a fixed synthetic goal; recorded prose cannot select another action or destination.

## Domain terms and ownership

| Term | Meaning |
|---|---|
| Selection | Explicit local configuration identifying one demonstration, PM store/task, Handoff store and disposable browser configuration. |
| Task claim | PM's live holder and generation for the selected task. A generation is a concurrency guard, not permission or a process kill mechanism. |
| Resource lease | The browser's native holder/session lifecycle; independently acquired for each worker. |
| Context record | One immutable Handoff revision, selected by task key and checked against an exact expected record and digest. “Handoff” describes this context, not transfer of a task claim. |
| Yield receipt | Profile-owned evidence of the producer's observed result, exact context record, clean resource release and observed PM yield. It grants no authority. |
| Operation receipt | Profile-owned correlation of an attempted command and its observed or unknown result. It is not a cross-component transaction journal. |

PM owns tasks, revisions, claims and task evidence. Handoff owns immutable context and selection assessments. Browser owns its resource lifecycle. The profile owns only its selection and receipts. All component state access uses installed public commands; no internal imports or direct component-store edits are allowed.

## Selection and identity decisions

The operator explicitly selects absolute executable paths and a new private workspace outside Git on a supported local filesystem. Component stores, anonymous browser state/profiles, client state and receipts live in separate children of that workspace. Never derive them from ambient estate settings. The workspace and profile files must belong to the current user, reject symlink traversal for owned writable paths, and use directories 0700/files 0600, independent of umask. Reject unexpected pre-existing paths instead of adopting or narrowing unrelated state.

The selection contains schema version 1, a UUID run ID, selected absolute paths, PM store ID and task ID, a task-definition digest, and one browser name/configuration. Define that digest over canonical JSON for the public task fields id, project, title, description and next_action (missing optional fields normalized to null); exclude status, ownership, evidence and timestamps. Canonical JSON uses sorted object keys, ASCII escaping, no extra whitespace and no trailing newline. Recheck it against the current task before and after claiming, so an edited goal cannot reuse old context. Paths are local configuration, not public receipt content. PM's observed store ID must match on every stateful reply. Handoff 0.1.0 exposes no store ID: bind its explicitly selected canonical path and run ID; never invent a component identity or claim to detect an identical store restored at that same path.

Derive the Handoff task key as `pm1-` plus the lowercase SHA-256 of UTF-8 JSON for `["orion-starter-continuity",1,pm_store_id,pm_task_id]`, with ASCII escaping, no extra whitespace and no trailing newline. This is a profile convention, not a new PM or Handoff field. Use `starter-<run UUID>` as the synthetic project key. Compare exact identities, never task titles, keywords or vendor conversation labels.

Use a profile-owned binding object in the context body: binding version, run ID, PM store ID, PM task ID, task-definition digest, producer claim generation and producer observation digest. Validate its exact shape and values; the generation is historical only. Keep the body at most 4 KiB and the complete record within Handoff's 64 KiB limit. Structured context fields describe the observed page and the remaining independent check. A recorded acceptance claim names only the synthetic demonstration baseline and its actual acceptance time; it does not assert that publication or any next action was approved.

After recording, the producer verifies `show` for the returned record ID/digest and current-tip status. The consumer uses exact-task `pickup` with an explicit 86,400-second age bound, then checks the selected ID against the yield receipt and the digest through `show`. It requires `authority: none`, valid integrity, `context_available`, an exact task match, a within-window observation, consistent recorded acceptance and the expected binding/evidence. A newly created successor requires fresh review and an explicitly selected replacement receipt; never silently follow it or fall back to an older revision. Project-resume selection is excluded from the execution path.

## Invocation and result contract

Provide a manually invoked example with three modes: **inspect**, **produce**, and **continue**. Each takes an explicit selection; continue also takes an explicit yield receipt. Produce and continue each create a unique worker-attempt ID and distinct PM/browser holders. Names never authenticate a person. No mode executes commands, references or next steps supplied in a context record.

Inspect performs only version/capability checks and selected PM/Handoff reads. It creates no stores/receipts, acquires no claims, and makes no browser lifecycle calls. Package installation and explicit synthetic-store/configuration setup are separate documented steps. A missing selection, empty object, incompatible version or unavailable executable cannot become a default selection.

Every invocation returns one bounded profile JSON result with profile interface version 1, mode, run/attempt IDs, state, failed operation if any, and independently observed component outcomes. States are `inspected`, `yielded`, `completed`, `refused` and `reconciliation_required`. Exit 0 is limited to the first three with their specific meaning; 2 means invalid invocation, 3 established refusal, and 7 unknown result/reconciliation required. An inspected context is not a successful yield or completed task.

Decode components separately. PM requires API 1, matching request ID, expected command/store/task, coherent exit/envelope/outcome and required capabilities. Handoff requires interface/store/record version 1 where exposed, `authority: none`, expected command and operation-specific result; it does not echo a PM-style request envelope. Browser requires the pinned package version and matching `ok`/`code`/`exit`/data; its version command is plain text. Validate every navigation-client batch result instead of searching arbitrary nested output for any matching title.

Bound subprocess output while receiving it: PM 8 MiB, Handoff 512 KiB, browser and navigation client 512 KiB each; stderr 64 KiB and profile output 64 KiB. Reject invalid UTF-8/JSON, duplicate keys, non-finite values, excessive nesting and inconsistent shapes. Do not keep accumulating output after the cap. Commands use argument arrays, no shell expansion, and only the selected minimal environment. Record no inherited environment, credentials or raw untrusted prose in public output.

Each external operation gets a unique profile operation ID. Pass PM request IDs and Handoff record request IDs where supported; other tools are correlated locally. Request IDs do not make a command idempotent. Before a mutating command, durably record its intent in a bounded private operation receipt, then record the observed outcome. If that write fails, do not launch the command. If the result/receipt is lost after launch, return unknown and stop forward work. See the [recovery runbook](../docs/runbooks/starter-continuity.md).

## Workflow invariants

1. Review the current user request and selected synthetic goal independently of context data. An invocation in this recipe authorizes only its documented synthetic read and coordination operations; the profile does not implement a general approval system.
2. Probe and claim the exact PM task through public commands. Re-read the live generation and selected task definition immediately before each new browser acquisition/action and each PM mutation; no losing, changed-goal or unknown claimant performs browser work. Do not automatically take over expired claims.
3. Generate a different browser holder for every attempt, within its native 64-character grammar. The same browser configuration/name may be reused only after observed cleanup; no old holder/session is passed to a successor.
4. The only navigation target is `https://example.com/`, expected URL exactly that value and title `Example Domain`. The client connects only to the validated loopback endpoint returned for the current lease and selected browser. Reject inherited browser/client connections, sessions and configuration overrides; no fallback or account sign-in.
5. Use a three-minute resource lease. Validate the session returned by the lease grant and recheck native holder/expiry/health before navigation. Browser 0.1.0 status does not expose a session ID; do not invent a session-fencing claim from that read. If insufficient time remains, stop and release rather than renew automatically. Component startup/stop deadlines must be derived from the selected browser configuration with bounded subprocess grace; a timeout does not prove the child or transient service stopped.
6. A successful observation requires the expected client result, native release with `stop=clean`, client-close acknowledgement, and native status `BROWSER_DOWN`/down/no holder. Follow the existing base walkthrough's order: release the native browser first, then close the client connection and check status. Closing the client first may close Chrome before its native owner can establish a clean stop. Client close must not start a replacement browser. A resource that is merely absent after an interrupted release is not proof that its previous stop was clean.
7. The producer records verified context only after browser cleanup. It then reads the exact record back, guarded-releases PM using its current revision/generation, and observes task todo/claim absent. Only then may it emit a successful yield receipt. Recording alone does not yield the task.
8. The consumer validates context before claiming, revalidates the exact current record/binding after acquiring its new generation, and then performs its own browser observation. It attaches only its current evidence through PM, uses the returned revision for guarded completion, and reads back done/claim absent. Producer evidence cannot substitute for this observation.
9. Unknowns stop forward work; cleanup may inspect and release only handles belonging to this attempt. Context refusal cannot itself mark a task done. If another actor has independently completed it, report that observed state without claiming this attempt completed it.
10. Context freshness is not current source compatibility. PM claim expiry is not execution fencing. Separate component checks cannot provide an atomic transaction or prevent an adversarial same-user process acting between checks. State these limits in every support claim.

## Acceptance scenarios and test seams

Primary seam: the manually invoked example over exact **installed CLIs and the real native browser/client**, exercised from an extracted candidate in fresh environments. Deterministic subprocess fixtures exercise refusal/interruption at that same example interface; they supplement, rather than replace, the native proof. No tests depend on private component modules. “Zero browser calls” in these criteria means zero lifecycle/navigation calls; plain version preflight is allowed. Implement one vertical scenario at a time with a RED→GREEN cycle.

| Scenario | Observable acceptance criteria |
|---|---|
| S1. Select and inspect | Fresh hash-locked installation succeeds without creating stores, enabling services or editing harness settings. Explicit setup creates only owned synthetic state. Inspect reports versions and selected identities without mutations. Missing/empty/wrong-store selections and missing executables fail visibly, with zero browser calls. The existing PM/browser profile remains usable. |
| S2. Produce a yield | A separately invoked producer claims, leases, reads, closes/releases, records and verifies exact context, then guarded-yields PM. Read-back is todo/claim absent; the receipt identifies the verified record/digest and actual observation. Failure at any stage prevents `yielded`. |
| S3. Continue and finish | A separate consumer selects the exact receipt/context, acquires a different live PM generation and different browser holder/session, independently observes the page, cleans up, attaches evidence and guarded-completes. Read-back is done/claim absent and browser down/no holder. Native receipts identify both attempts and their distinct handles. |
| S4. Refuse unusable context | Missing selector/store, empty/incomplete data, stale/future/done context, conflicting acceptance, missing evidence, wrong store/run/task, changed record/digest, malformed/oversized output and interrupted pickup prevent browser acquisition/completion. No older/latest/project fallback. A project-only ambiguity diagnostic remains an established Handoff exit 11, not a usable continuation. |
| S5. Contend and lose ownership | Two consumer processes start together after the producer yields. Exactly one claims; the loser makes zero browser calls. A separate fixture changes/expires the winner's generation or resource holder before its next action: the attempt stops, does not use the stale handle or release another holder, and cannot claim completion. |
| S6. Interrupt and reconcile | Inject interruption before launch and after possible commit at claim, browser acquisition/read/close/release, record, PM yield, evidence attachment and completion. Inspect the correct component without blind replay. A read-only diagnostic distinguishes refusal, unavailable and unknown; a later explicitly invoked repaired attempt must supply fresh observations and handles. Unknown cleanup never produces a successful receipt. |
| S7. Package and remove safely | Verify artifact/lock/example digests and MIT notices from a clean extracted candidate; rerun both documented profile entry paths. A tampered digest, missing check or unexpected archive member fails. Preserve the RC2 archive. After explicit owned-resource cleanup, uninstall removes only selected disposable state/environments; unrelated state is unchanged. Restore uses matching component artifacts/backups, with no claimed migration or automatic downgrade. |

S1–S7 are future acceptance requirements, not results already achieved. The earlier 16-command PM/Handoff feasibility probe does not establish the native three-component workflow. Native Claude/Codex/Grok/Dot support and stable-distribution onboarding require separate actual-harness/newcomer evidence; neither is needed to describe this preview truthfully.
